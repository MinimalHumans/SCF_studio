## The problem

What is wrong or missing today, stated so that someone who disagrees
with your solution still agrees with this paragraph. Where you can,
point at something concrete — a query that cannot be answered, a rule
two implementations read differently, a finding nothing raises.

If you have hit this while implementing, say so and say where. A problem
that has actually bitten someone is worth more than one that might.

## The proposal

What you want to change. Be specific enough that a reader can tell
whether an implementation conforms to it. If it changes a normative
rule, write the replacement wording.

## What it breaks

Every change breaks something, and "nothing" is almost always wrong.
Name it: files already written, implementations already built, other
rules that assume the current behaviour. Per spec §11.0 breaking
existing `.scf` files is cheap before 1.0 — but it is only cheap if it
is said out loud rather than discovered later.

## Alternatives

What else would solve the problem, and why this one instead. **Including
doing nothing.** A proposal that cannot say what is wrong with leaving
things alone usually has not found the real constraint yet.

## Unresolved

What you do not know. Questions for the discussion rather than
statements. It is fine — often better — to open a proposal with this
section full.
